# CSF Food Flow PWA

The frontend for the Cambridge Sustainable Food App — a Progressive Web App
for recording weigh-in/weigh-out events at hubs and the food centre,
designed to work offline on a phone or tablet at the point of weighing.

## Architecture Overview

- **Framework**: Preact + `@preact/signals` (not React — same mental
  model, ~4KB runtime)
- **Build tool**: Vite + `@preact/preset-vite`
- **Styling**: Tailwind CSS v4 (CSS-native `@theme`, real brand colors
  extracted from CSF's logo/favicon)
- **Routing**: `preact-router`
- **Data fetching**: native `fetch()`, `credentials: 'include'` for the
  httpOnly session cookie
- **Contract safety**: TypeScript types in `src/types/api.ts` are
  **mechanically generated** from `docs/openapi.yaml` (the same file
  canonically owned by the API repo) — not hand-copied
- **Offline**: `vite-plugin-pwa` (Workbox) caches the app shell only. The
  app itself keeps what the forms need on the device (signed-in user,
  locations, categories, tray types) and queues entries recorded without a
  connection, uploading them automatically. See "Offline and shared
  devices" below.

## Package Structure

```
src/
  components/     -- NavBar, RouterLink (typed preact-router wrapper)
  pages/          -- one file per route (Login, WeighIn, Entries, etc.)
  services/
    api.ts           -- typed API client; tells "no connection" apart from "refused"
    submitEntry.ts   -- saves one entry and decides what happens if that fails
  store/
    session.ts       -- signed-in user, offline start, sign-out
    offlineQueue.ts  -- entries waiting to upload, each tagged with who recorded it
    autoSync.ts      -- uploads waiting entries automatically
    referenceData.ts -- device copies of locations, categories, tray types
  utils/
    storage.ts       -- localStorage helpers that never throw
  types/
    api.ts            -- GENERATED from docs/openapi.yaml, do not hand-edit
    entry-form-schema.ts -- Zod validation for the weigh-in/out form
docs/
  openapi.yaml    -- copy of the canonical contract (see docs/CONTRACT.md)
public/
  icons/          -- generated from the real CSF favicon mark
  manifest is generated by vite-plugin-pwa from vite.config.ts
```

## Offline and shared devices

The app is built for a hub tablet shared by several volunteers, often in a
building with poor signal.

**Opening the app with no connection.** The last signed-in person and the
lists the forms need are kept on the device, so the app opens and records
as normal. Signing in itself needs a connection.

**Saving an entry.** What happens depends on why a save fails:

| Failure | What the app does |
|---|---|
| No connection, or a server error (5xx, e.g. a cold start) | Keeps the entry on the device; it uploads automatically |
| Session ended (401) | Keeps the entry, sends the person to sign in; it uploads once they have |
| Refused (other 4xx) | Shows the server's message and keeps the form filled in; nothing is saved |

**Automatic upload.** Waiting entries upload when the connection comes
back, when the app opens, after signing in, after any successful save,
and every minute while something is waiting. Only one upload runs at a
time, and re-sending is safe (`client_uuid` makes it idempotent).

**Shared tablets.** Each waiting entry records who entered it, and only
uploads under that person's sign-in -- never under the next volunteer's.
The weigh forms always show who is recording, with a one-tap sign-out.
Signing out uploads that person's waiting entries first, then expires the
session cookie on the server (`POST /auth/logout`); clearing local state
alone would leave the cookie valid for the next person. If the sign-out
can't reach the server, the device stays signed out until it can.

**Service worker.** API responses are deliberately not cached by the
service worker: a cached `/me` would bring the previous volunteer back
after sign-out. The app manages its own device copies and clears them on
sign-out.

## Prerequisites

- Node.js 20+
- The API running locally (see `csf-food-flow-api`'s README) or a deployed
  API URL to point at

```bash
npm install

```

## Local Development Commands

```bash
npm run dev              # dev server, http://localhost:5173
npm run dev -- --host    # also reachable from your phone on the same wifi

npm run typecheck        # tsc --noEmit, strict mode
npm run lint              # ESLint
npm run test              # Vitest (offline, sync and session logic, currently 63 tests)
npm run test:e2e           # Playwright (not yet populated with flows)
npm run format              # Prettier

npm run generate:types       # regenerate src/types/api.ts from docs/openapi.yaml
```

## Build Commands

```bash
npm run build   # tsc -b && vite build -- output in dist/

```

## Deployment Notes

**PWA → Netlify** (`netlify.toml` provided):
1. Netlify → Add new site → import this repo. It reads `netlify.toml`
   for the build command, publish directory, SPA fallback and API proxy.
2. **Do not set `VITE_API_URL`** in Netlify. With it unset, the client
   calls the relative path `/api/v1`, and `netlify.toml` proxies `/api/*`
   to the API on Azure Container Apps server-side. The browser only ever
   talks to the PWA's own origin, which keeps the session cookie
   first-party in Safari and private browsing.
3. If the API's URL changes, update the `to =` line of the `/api/*`
   redirect in `netlify.toml`. That is the only place it lives.
4. In the API's Azure Container Apps configuration, set `CORS_ORIGIN` to
   this site's exact Netlify URL (not a wildcard).

**API → Azure Container Apps**: see `csf-food-flow-api`'s README. The API
scales to zero when idle, so the first request after a quiet period can
be slow. Entries recorded during that window are queued offline and sync
automatically.

**Database → Neon**: no PWA-side deployment step; the PWA only talks to
the API, never directly to the database.

## Continuous Integration

`.github/workflows/ci.yml` runs on every push and pull request. It checks
that `src/types/api.ts` matches `docs/openapi.yaml`, then runs typecheck,
lint, the tests and a build.

Netlify deploys `main` on its own, independently of this workflow, so a
failing check doesn't stop a deploy by itself. To make the checks a gate,
work through pull requests, and in GitHub (Settings → Branches) protect
`main` so the "Typecheck, lint, test, build" check must pass before
merging.

## Contract Sync

`docs/openapi.yaml` here is a **copy** of the canonical file in the API
repo. When the API's contract changes:
1. Copy the updated `docs/openapi.yaml` from the API repo into this one
2. Run `npm run generate:types`
3. Commit both the updated spec copy and the regenerated `src/types/api.ts`
   together

See `docs/CONTRACT.md` for the full discipline and why this isn't a single
shared package (two repos, two languages — see the root of this project's
build history for the reasoning).

## Known Assumptions / TODOs

- **A1** — `EntryDetail` (`/entries/:entryId`) fetches via the list
  endpoint and filters client-side, rather than calling `GET /entries/{id}`
  directly. The contract supports the dedicated endpoint; wiring
  `services/api.ts` to use it is a small follow-up.
- **A2** — `AdminUsers` uses a raw `fetch()` call instead of the typed
  API client, for the same reason as A1 (page-priority ordering meant
  admin pages were built last, after the higher-priority weigh-in/out and
  sync flows).
- **A3** — Admin pages (`/admin/locations`, `/admin/users`) are read-only
  in this pass. The API already supports create/update
  (`POST`/`PATCH` on both resources, ADMIN-only, verified working) — the
  forms themselves are a follow-up.
- **A4** — `npm install` requires TypeScript pinned to `5.9.3` (not the
  newer `6.x` Vite's template defaults to) because `openapi-typescript`
  declares a peer dependency on TS `^5.x`. This is already reflected in
  `package.json`; just don't bump TypeScript without checking
  `openapi-typescript`'s peer range first.
- **A5** — Playwright is installed but no E2E flows are written yet. The
  offline, sync and sign-out logic is unit-tested (Vitest), but the
  highest-value browser flow is still manual: create an entry while
  online, go offline, create another, verify it waits, restore the
  connection, verify it uploads on its own and clears.
- **A6** — Branding: theme color `#8A4097` and background `#FFFFFF` were
  extracted directly from the real `CSF_logo.png` / `favicon-CSF.webp`
  files, not estimated. If those source files change, regenerate
  `public/icons/*.png` and update the two hex values in
  `vite.config.ts`/`src/index.css` together.
