# CSF Food Flow PWA

[![CI](https://github.com/mateador/csf-food-flow-pwa/actions/workflows/ci.yml/badge.svg)](https://github.com/mateador/csf-food-flow-pwa/actions/workflows/ci.yml)

The frontend of the Cambridge Sustainable Food App's Food Flow Log: a
Progressive Web App for recording food arriving at and leaving community
hubs and the food centre, weighed at the point of collection. It replaces
the paper weigh-in and weigh-out sheets the hubs used before.

It's built for how the hubs actually work: a tablet shared by several
volunteers, often in a building with weak signal. Everything a volunteer
does at the counter works offline.

**Status:** in trial with volunteers at CSF hubs, ahead of an adoption
decision. The backend is
[csf-food-flow-api](https://github.com/mateador/csf-food-flow-api).

## What it does

| Screen | Who | What |
|---|---|---|
| **Food In** (`/weigh-in`) | Everyone (hub volunteers at their own hub only) | Record food arriving: where it came from ("From"), category, gross weight and trays. Net weight is worked out from the trays |
| **Food Out** (`/weigh-out`) | Food centre, admin | Record food leaving the centre for a hub |
| **Entries** (`/entries`) | Everyone (hub volunteers see their own hub) | Recent entries, with details |
| **Weekly report** (`/reports/weekly`) | Everyone (hub volunteers see their own hub) | Monday-to-Sunday totals by category, location and source. Admins can export CSV |
| **Sync** (`/sync`) | Everyone | Entries waiting to upload, any the server refused, and other volunteers' waiting entries on this device |
| **Settings** (`/settings`) | Everyone | Display preferences, and sign-out |
| **Admin** (`/admin/...`) | Admin | Locations, source locations ("From" list) and users. Read-only for now, see A2 |

Roles are enforced by the API on every request. The screens only decide
what to show.

## Architecture Overview

- **Framework**: Preact + `@preact/signals` (not React — same mental
  model, ~4KB runtime)
- **Build tool**: Vite + `@preact/preset-vite`
- **Styling**: Tailwind CSS v4 (CSS-native `@theme`, real brand colors
  extracted from CSF's logo/favicon)
- **Routing**: `preact-router`
- **Data fetching**: native `fetch()`, `credentials: 'include'` for the
  httpOnly session cookie
- **Validation**: Zod schemas for the weigh forms
  (`src/types/entry-form-schema.ts`); the API validates everything again
- **Contract safety**: TypeScript types in `src/types/api.ts` are
  **mechanically generated** from `docs/openapi.yaml` (the same file
  canonically owned by the API repo) — not hand-copied
- **Offline**: `vite-plugin-pwa` (Workbox) caches the app shell only. The
  app itself keeps what the forms need on the device (signed-in user,
  locations, categories, tray types) and queues entries recorded without a
  connection, uploading them automatically. See "Offline and shared
  devices" below.

## Offline and shared devices

The app is built for a hub tablet shared by several volunteers, often in a
building with poor signal.

**Opening the app with no connection.** The last signed-in person and the
lists the forms need are kept on the device, so the app opens and records
as normal. Signing in itself needs a connection.

**Saving an entry.** What happens depends on why a save fails:

| Failure | What the app does |
|---|---|
| No connection, or a server error (5xx, e.g. a cold start) | Keeps the entry on the device; it uploads automatically |
| Session ended (401) | Keeps the entry, sends the person to sign in; it uploads once they have |
| Refused (other 4xx) | Shows the server's message and keeps the form filled in; nothing is saved |

**Automatic upload.** Waiting entries upload when the connection comes
back, when the app opens, after signing in, after any successful save,
and every minute while something is waiting. Only one upload runs at a
time, and re-sending is safe (`client_uuid` makes it idempotent).

**Shared tablets.** Each waiting entry records who entered it, and only
uploads under that person's sign-in -- never under the next volunteer's.
The weigh forms always show who is recording, with a one-tap sign-out.
Signing out uploads that person's waiting entries first, then expires the
session cookie on the server (`POST /auth/logout`); clearing local state
alone would leave the cookie valid for the next person. If the sign-out
can't reach the server, the device stays signed out until it can.

**Service worker.** API responses are deliberately not cached by the
service worker: a cached `/me` would bring the previous volunteer back
after sign-out. The app manages its own device copies and clears them on
sign-out.

**Session ended mid-use.** If any request finds the session gone (it
expired, or an admin deactivated the account), the app signs out and says
why, instead of leaving a half-empty screen.

## Data kept on the device

Everything is in `localStorage`, on that device only:

| What | Why | When it's removed |
|---|---|---|
| The signed-in person (name, email, role, hub) | So the app opens with no signal | On sign-out, or when the server says the session has ended |
| Locations, categories, tray types, source locations | So the forms work offline | On sign-out, and refreshed on every sign-in |
| Entries waiting to upload, each with who recorded it | So nothing recorded offline is lost | Once uploaded, or discarded on the Sync page |
| Display preferences | A per-tablet setting | Never: they belong to the device, not a person |

Waiting entries deliberately survive sign-out. They upload the next time
the person who recorded them signs in on that device.

## Display preferences

Three independent toggles in Settings (`src/store/theme.ts`), each a
per-device `localStorage` preference rather than a user account setting
-- a tablet mounted at a hub counter can have one turned on once and it
stays on for that device only, without affecting anyone's own phone:

- **High contrast** -- darker text/borders on the normal bright
  background, for reading in direct sunlight/glare.
- **Large text** -- scales the whole UI's root font size up, for a
  tablet viewed from counter distance.
- **Dark mode** -- a genuine dark theme (not the same thing as High
  Contrast -- that one assumes a bright page), for low light.

All three use the same mechanism: a `data-*` attribute set on `<html>`
before first paint (see the inline script in `index.html`, which avoids a
flash of the default theme), with the actual styling done in
`src/index.css` as attribute-selector overrides of the Tailwind color/size
variables already used throughout the app, rather than touching component
markup.

**They are deliberately cross-aware.** High Contrast and Dark Mode can
both be on at once, and High Contrast's overrides were written to check
for that (`:not([data-theme='dark'])` vs. `[data-theme='dark']` variants
of each rule) -- a hardcoded "force this text pure black" only helps on a
bright background, and does the opposite of "high contrast" on a dark
one. If you add a fourth display toggle, check how it behaves combined
with the other three before shipping it, not just on its own.

Also worth knowing: Tailwind v4's default color palette uses `oklch()`
colors, which older/budget Android browsers (this app's actual hub
tablet is a several-years-old ASUS ZenPad) don't parse -- an unparseable
background-color silently falls back to transparent, not to the color
you'd expect. Every default-palette shade this app actually uses
(neutral/red/green/amber) is redefined as plain hex in `src/index.css`'s
`@theme` block for exactly this reason; don't reintroduce a raw Tailwind
color utility without checking it's covered there.

## Testing

**Automated (Vitest, 63 tests).** These cover the parts most likely to
lose someone's data if they broke:

- `src/store/offlineQueue.test.ts`: queueing, per-volunteer ownership,
  one upload at a time, refused entries kept with their reason, entries
  from older app versions;
- `src/store/autoSync.test.ts`: when uploads happen, and what happens on
  no connection or an ended session;
- `src/store/session.test.ts`: offline start, real sign-out, a sign-out
  that couldn't reach the server, an ended session;
- `src/services/submitEntry.test.ts`: saved, kept for later, signed out,
  or refused;
- `src/services/api.test.ts`: telling "no connection" apart from
  "refused";
- `src/store/referenceData.test.ts`: device copies used offline, and
  never hiding a 401.

**On a real device (manual, before a release that touches offline
behaviour).** Use the hub tablet if possible:

1. Sign in with a connection, then close the app, turn on airplane mode
   and reopen it. It opens signed in, and the forms have their lists.
2. Record an entry offline. Turn airplane mode off and wait. It uploads on
   its own within a minute.
3. As volunteer A, record an entry offline and sign out. Sign in as
   volunteer B: A's entry waits and is **not** uploaded under B. Sign in as
   A again, and it uploads.
4. Sign out, close and reopen the app. It shows the sign-in screen, not
   the previous person.

## Deployment Notes

**PWA → Netlify** (`netlify.toml` provided):
1. Netlify → Add new site → import this repo. It reads `netlify.toml`
   for the build command, publish directory, SPA fallback and API proxy.
2. **Do not set `VITE_API_URL`** in Netlify. With it unset, the client
   calls the relative path `/api/v1`, and `netlify.toml` proxies `/api/*`
   to the API on Azure Container Apps server-side. The browser only ever
   talks to the PWA's own origin, which keeps the session cookie
   first-party in Safari and private browsing.
3. If the API's URL changes, update the `to =` line of the `/api/*`
   redirect in `netlify.toml`. That is the only place it lives.
4. In the API's Azure Container Apps configuration, set `CORS_ORIGIN` to
   this site's exact Netlify URL (not a wildcard).

**API → Azure Container Apps**: see `csf-food-flow-api`'s README. The API
scales to zero when idle, so the first request after a quiet period can
be slow. Entries recorded during that window are queued offline and sync
automatically.

**Database → Neon**: no PWA-side deployment step; the PWA only talks to
the API, never directly to the database.

## Continuous Integration

`.github/workflows/ci.yml` runs on every push and pull request. It checks
that `src/types/api.ts` matches `docs/openapi.yaml`, then runs typecheck,
lint, the tests and a build.

Netlify deploys `main` on its own, independently of this workflow, so a
failing check doesn't stop a deploy by itself. To make the checks a gate,
work through pull requests, and in GitHub (Settings → Branches) protect
`main` so the "Typecheck, lint, test, build" check must pass before
merging.

## Contract Sync

`docs/openapi.yaml` here is a **copy** of the canonical file in the API
repo. When the API's contract changes:
1. Copy the updated `docs/openapi.yaml` from the API repo into this one
2. Run `npm run generate:types`
3. Commit both the updated spec copy and the regenerated `src/types/api.ts`
   together

Two CI checks back this up. This repo's CI fails if `src/types/api.ts`
doesn't match this repo's `docs/openapi.yaml`. The API repo's CI warns if
the two `openapi.yaml` copies differ. See `docs/CONTRACT.md` for why this
is a copied spec file rather than a shared package (two repos, two
languages).

## Known Assumptions / TODOs

- **A1** — `EntryDetail` (`/entries/:entryId`) finds an entry by fetching
  the newest 100 entries and filtering, so an older entry's detail page
  shows "not found". `GET /entries/{id}` is described in
  `docs/openapi.yaml`, but the API doesn't implement it yet (see the API
  README, A6). Implementing it there, then calling it here, is the fix.
- **A2** — Admin pages (`/admin/locations`, `/admin/users`,
  `/admin/source-locations`) are read-only in this pass. The API already
  supports create/update (`POST`/`PATCH` on all three resources,
  ADMIN-only, verified working). The forms themselves are a follow-up.
- **A3** — TypeScript stays on 5.x (`^5.9.3`, not the 6.x Vite's template
  defaults to), because `openapi-typescript` declares a peer dependency on
  TS `^5.x`. Don't bump TypeScript without checking `openapi-typescript`'s
  peer range first.
- **A4** — Playwright is installed but no E2E flows are written yet. The
  offline, sync and sign-out logic is unit-tested (Vitest), but the
  browser journey is checked by hand (see "Testing"). The first flow to
  automate is checks 1 and 2 there.
- **A5** — Branding: theme color `#8A4097` and background `#FFFFFF` were
  extracted directly from the real `CSF_logo.png` / `favicon-CSF.webp`
  files, not estimated. If those source files change, regenerate
  `public/icons/*.png` and update the two hex values in
  `vite.config.ts`/`src/index.css` together.
- **A6** — The weigh forms default the collection date in UTC. Between
  midnight and 1am UK time in summer, they suggest yesterday's date. That's
  outside hub hours, so it's low impact.
